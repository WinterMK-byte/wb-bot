# 新成员接入（含全员知会）

## 核心判据：写进注册表 ≠ 通知到位

新人接入最容易漏的一步：**把新成员写进注册表，然后以为大家都知道了**。

事实是：**没有任何 Agent 会主动去读注册表**。
所以"写进注册表"只提供了"可查证"，**没有提供"已通知"**。

> 正确做法：既要写注册表（可查证），**也要写进注入点**（真正通知）。

## 标准动作（七步）

```
① 判定席位        他属于哪层？（协调 / 业务负责人 / 执行者）
② 写席位注册表     只追加新版本节，更新顶部"现行版本"指针
③ 写角色卡         他是谁 / 管什么 / 边界在哪
④ 同步注入点       ★ 关键：凡是"每个 Agent 启动必读"的地方都要更新
⑤ 登记总线         四要素：新增了什么 / 为什么 / 影响面 / 回滚点
⑥ 备份             改前先备份，留可还原点
⑦ 通报            在总线里 @ 相关成员
```

## ★ 第四步：注入点（这是最容易漏的）

**判断某处要不要加**，不是"相关就加"，而是：

> **「不写进这里，某个 Agent 就真的不知道」** → 才加。

典型的注入点：
- 共享的身份文件（每个 Agent 启动时读）
- 启动脚本 / 引导文档
- 路由卡（查"这句话归谁"时会读）

**为什么这一步是决定性的**：只在文档里写了"本机新增了一个成员"，
但每个 Agent 启动时读的是**另外几个文件** —— 那它们**永远不知道**新成员存在。

→ 详见 `docs/05-injection.md`。

## 接入检查清单

```
[ ] 席位已定（属于哪层）
[ ] 注册表已追加新版本节 + 指针已更新
[ ] 角色卡已写（含边界）
[ ] 注入点全部同步（逐一列出名字，别笼统说"已同步"）
[ ] 总线已登记四要素
[ ] 改前备份已做、可还原
[ ] 相关成员已通报
```

## 改定义的连带影响

| 改什么 | 要不要同步注入点 |
|---|---|
| 改**席位定义**（层数 / 职责） | **必须**同步全部注入点 |
| 只加**资产归属**（某文件归到某线） | 不必同步定义，但归属表要更新 |

## 反例警示

**"没人管 ≠ 需要一条线"**。
新开一条业务线的判据是三条**同时**满足：
1. 有持续迭代需求
2. 有独立产物
3. 每周至少动一次

不满足 → **归协调者代管**，别新开线。
