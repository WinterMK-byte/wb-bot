# 09 · 多调度源

> 只要一台机器上跑过几个月的自动化，**定时任务一定会散在多个地方**。
> 这一篇讲清四类调度源的口径差异，以及不管用哪个都必须守的纪律。

---

## 一、现实：调度源不止一个

自动化任务会从这些地方长出来：

| 源 | 典型形态 | 谁建的 |
|---|---|---|
| **A. 应用内自动化** | 某个 GUI 应用的定时功能 | 用户点出来的 |
| **B. 另一个应用的 cron** | 标准 cron 表达式 | 用户/脚本 |
| **C. 本机自建守护** | 一个常驻 Python 脚本轮询 `due()` | 工程师 |
| **D. 操作系统计划任务** | OS 级 scheduler | 脚本 / 安装器 |

**它们口径完全不同** —— 这不是设计问题，是历史必然（每个应用有自己的调度实现）。
**能做的是搞清差异、统一纪律，而不是强行合并。**

---

## 二、四源口径对照

| 项 | A. 应用内 | B. cron | C. 本机守护 | D. OS 计划任务 |
|---|---|---|---|---|
| 时间表达 | 多为 RRULE | 标准 cron（段数各平台不同） | 自定义 `due()` | XML / 图形化 |
| **错过怎么办** | **补跑** | **记 miss，不补跑** | 看实现 | 看配置 |
| 依赖什么 | **应用得在运行** | 常驻服务 | 守护脚本得活着 | OS 服务 |
| 时段过滤 | 弱（见下） | 强（支持范围） | 可自建 | 可配 |
| 历史记录 | 应用自己的库 | 日志 | 自己的 log | 事件日志 |

**这张表的意义**：同一个"每天早上 7 点"写在四个地方，**实际行为可能完全不同**。
所以"我在 A 里配了 7 点"和"我在 B 里配了 7 点"不能当成等价。

---

## 三、四个真实陷阱

### 3.1 RRULE 的 `BYHOUR` 只吃单个整数

想配"每天 9 点、12 点、18 点" → 写 `BYHOUR=9,12,18` → **被拒**。

结论：遇到只吃单值的调度实现，**高频任务限不了时段** → 只能降频，或在**任务内容里加时间守卫**（见 §四）。

### 3.2 "高频 + INTERVAL" 的真实语义 ≠ 你写的

某些实现的 `HOURLY;INTERVAL=N` 实际是"**上次运行 + N 小时**"，
间隔会**恒定地差一点并持续漂移**（因为上次运行本身有耗时）。

→ 想整齐地"每小时整点"，要么用能表达"绝对时刻"的源，要么接受漂移。

### 3.3 错过补跑 ≠ 错过不补 —— 这才是最危险的

- **补跑型**（A）：机器关机期间错过了，**开机瞬间会补**
- **不补型**（B）：错过了就是 `miss`，不会追

**"补跑"是最大的隐藏风险**：如果任务假定"我每天只跑一次、且跑的是当天数据"，
开机补跑可能导致它**在错误的时刻用错误的数据跑一遍**。

→ 任何"补跑型"任务都必须有**时段守卫**（见 §四）。

### 3.4 `due()` 用 `>=` 语义 → 开机瞬间集中补跑

自建守护最常见的写法：`if now >= next_run: run()`。
如果机器关机 8 小时，`now` 已经远超 `next_run` → **开机瞬间把 8 小时内的任务全补一遍**。

→ 修法：加**运行窗口**判断（`RUN_START` / `RUN_END`），窗口外不跑。

## 四、统一纪律（不管用哪个源）

### 4.1 时段守卫：自动任务不得落在"机器不开机"的时段

如果这台机器晚上会关机/断电，那么：

> **任何自动任务、定时脚本、守护进程的触发时间，必须落在机器开机时段内。**

理由有两个，缺一不可：
1. 关机时任务本来就不会执行（白配）
2. 但"补跑型"调度会在开机瞬间把错过的**全补一遍** ← 真正的风险

**落地做法**：
- 能配时段的源 → 直接限制时段（如 cron 的 `6-22`）
- 不能配的源（如 §3.1）→ 在**任务 prompt 里加时间守卫**（开头判断当前时间在不在窗口内，不在就退出）
- 自建守护 → 加 `in_window()` 前置检查

### 4.2 路径有效性：写死的绝对路径会静默失效

**这是最贵的一个坑。**

任务 prompt 里写死了 `…/old-plan.md` 来读数据。
某天这个文件**被迁移或改名了** → 任务每天的运行结果是："读空 / 报文件不存在"。

**为什么最贵**：它**不报错给任何人**。任务照跑、照记"文件不存在"，
直到某天有人去看产出才发现**产出已经空了很久**。

**纪律**：
- 盘点任何自动化时，**必须逐一 `exists` 验证**任务里写死的每一个路径
- 迁移文件时，**必须反查哪些任务引用了它**（`grep` 全库）
- 优先让任务**动态定位**（按日期/模式匹配），而不是写死文件名

→ 见 [教训 04](lessons.md#04-写死的绝对路径)。

### 4.3 僵尸任务

迁移（换机器/换应用）之后，旧调度源里的任务**不会自己消失**，但**再也不会执行**。

它们会：
- 让盘点变难（分不清"活着的"和"僵尸"）
- 制造错觉（"我有 17 个任务在跑" —— 其实全死）

**纪律**：迁移后**必须做一次全源盘点**，把僵尸任务显式标记或移走（**移动而非删除**，保留可还原）。

### 4.4 幂等与状态

补跑 + 不幂等 = 灾难。
任何会被补跑的任务，其副作用必须**幂等**（或自带"今天已做过"的状态检查）。

## 五、盘点清单（迁移后 / 定期）

```
① 列出所有调度源
② 每个源：导出全部任务（含触发时间、内容、状态）
③ 对每个任务：
   - 它引用的路径，逐一 exists 验证      ← 最常抓出真问题
   - 它上次实际执行是什么时候（看历史记录）
   - 是"僵尸"吗（迁移后从未执行）
④ 交叉查重：同一个任务是否在多个源里各配了一份
⑤ 时段检查：有没有落在关机时段的
⑥ 输出：一张全景表（源 / 数量 / 活跃 / 僵尸 / 风险）
```

**验收判据**：每个"活跃"任务都能**指出它最近一次真实执行的证据**（执行记录 / 产出文件时间戳）。
没有证据的"活跃" = 实际僵尸。

## 六、踩过的坑汇总

| # | 坑 | 后果 |
|---|---|---|
| 1 | RRULE 只吃单值 BYHOUR | 时段限制做不了 → 得用 prompt 守卫 |
| 2 | INTERVAL 语义漂移 | 间隔不准 |
| 3 | 补跑型在开机瞬间集中补 | 按错误时间/数据跑一遍 |
| 4 | **写死路径静默失效** | **产出默默变空，无人察觉** |
| 5 | 僵尸任务 | 盘点失真 |
| 6 | 多源重复配置 | 同一件事跑两遍 |
