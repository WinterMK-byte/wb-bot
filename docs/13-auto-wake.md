# 13 · 一句话派单与自动唤醒（Auto-Wake）

> **这一篇回答一个问题**：
> *我说一句话，系统能不能自己把活安排下去、还能让"没开着的会话"真的动起来？*
>
> **答案：能。** 但**必须先把两个事实搞清楚**，否则你会设计出一个"看起来自动、其实不动"的系统。
> 本文含**实测数据**（不只是设计）。

---

## 一、先破除一个幻觉：会话**不会**被唤醒

| 场景 | 能自动吗 |
|---|---|
| 你在**当前会话**说话 | ✅ 它立刻做 |
| 你希望**别的会话**也动 | ❌ **它没开着 = 没在跑**，听不到你说话 |
| **调度系统的任务触发** | ✅ **能自动跑**（不需要你开着任何会话） |

**关键区别**：
- 「会话」是**活的进程** —— 没开就是没在跑，**不可能"收到"任何东西**
- 「调度任务」是**系统级的定时器** —— 到点就**新建一个会话实例**去干活，**不需要你开着任何窗**

⇒ **所以"自动唤醒"的唯一可靠手段 = 调度系统的一次性任务。**

**推论（很重要）**：
- 只把单子写进"共享日志"、然后期待对方"看到" ⇒ **它看不到**，因为它可能压根没开着
- 想让它**真的动** ⇒ **投递 + 唤醒**，两件都要

---

## 二、破解：把"唤醒"当作派单的最后一步

```
你说：「让 X 组检查 Y」
        │
        ▼
【调度会话】立即执行四步：
   ① 写单           → 结构化文档（要素见 12 号文档 §五）
   ② 投递           → 收件箱 + 贴到 X 组工作区（双通道）
   ③ ★ 建一次性任务  → N 分钟后，在 X 组工作区触发：
        「读 <单子路径> 并执行；完成后按交接纪律回执」
   ④ 登记日志
        │
        ▼
【N 分钟后】X 组会话被**自动启动** → 读单 → 干活 → 回执
        │
        ▼
【调度会话】读到回执 → 报你结果
```

**这就是「一句话 → 自动安排 → 自动执行」。**

---

## 三、实测数据（真实跑过，不是设计）

**实验**：建一个一次性任务，让它在**调度会话之外**自动跑一次、写个文件证明它真启动了。

```text
建单    : 19:57:05
预定触发: 20:00:00
实际开始: 20:00:28      ← ★ 延迟 28 秒
完成    : 20:00:36
```

**三重证据**（★ 缺一不可 —— 单看一个都可能被"假象"骗）：

| 证据 | 内容 |
|---|---|
| ① **产物文件** | 生成了 `_wake_test.txt`，内容含真实时间戳 |
| ② **执行记录表** | `20:00:28 / status=ACCEPTED / result_success=1` |
| ③ **记录标题** | 「唤醒能力实测通过。已将当前本地时间写入…」 |

**关键**：**全程调度会话没做任何操作** —— 是任务让会话自己醒过来干的。

> **为什么强调三重证据**：只看文件 → 可能是别的东西写的；
> 只看记录 → 可能记录了但没真跑。**三者交叉才算证完。**（同 06 号教训）

### ★ 延迟特性（设计时必须知道）

**预定 20:00:00，实际 20:00:28 —— 约 30 秒延迟。**

⇒ **唤醒不是瞬时的**。
- 别指望"说完立刻动"
- **1–2 分钟的延迟是正常的**，不是故障
- 对用户的预期要按「**分钟级**」而不是「秒级」

---

## 四、两条路（推荐 A）

| | **A · 即时唤醒**（推荐） | B · 总管巡检 |
|---|---|---|
| 怎么触发 | 你说一句 → 调度会话**顺手建**唤醒 | 定时任务每隔 N 分钟**扫收件箱** |
| 精准度 | ★ **按需** —— 只唤醒该唤醒的 | 无差别扫，可能空跑 |
| 成本 | ★ **省**（有活才烧） | **费**（固定频率烧，哪怕没事） |
| 适合 | 日常 | 你希望**完全不开口**时的兜底 |

**推荐 A**：精准、省、可控。
**B 作兜底**：防止"你说了但调度会话没记"（但**B 会无差别烧钱**，慎开）。

---

## 五、代价与边界（**不可省**）

| 项 | 情况 |
|---|---|
| **成本** | 每次唤醒 = 目标会话跑一轮 ⇒ **产生一次模型调用开销**。**这是"自动"的代价** |
| **时段** | 唤醒时间必须落在**你的可用时段内**（本机铁律：**06:00–23:00**） |
| **可靠性** | ★ 被唤醒的**仍然是 agent** —— 它可能偷懒、跑偏、甚至说"做完了"却没做（见 12 号事故）。**所以回执 + 独立复核不能省** |
| **不能并跑** | 各会话**串行**（同一时刻只跑一个），**不存在真并行** |
| **硬限制** | ❌ **不能"让所有会话都醒着"** —— 既不可能（资源），也没必要（会乱）。**按需唤醒才是对的方向** |

> ★ **最容易犯的错**：以为"自动唤醒"= "全自动无人管"。
> 它**只是把"手动打开会话"这一步自动化了** —— **判断、验收、纠偏仍然需要人**。

---

## 六、落地检查清单（照做即可）

- [ ] 投递**落到对方启动必读的位置**（不是只写日志）
- [ ] 唤醒任务**建在目标工作区**（`cwd` 必须是那个工作区）
- [ ] 任务 prompt **自包含**：单子路径 + "做完按交接纪律回执"
- [ ] 指定**模型**（若平台需要显式指定 —— 本机实测：`modelId` 参数可用；不指定会用默认模型，**可能与预期不符**）
- [ ] 触发时间**落在允许时段内**
- [ ] 延迟按 **1–2 分钟**预估
- [ ] ★ 完成后**出单方独立复核**（不看回执看实测）

---

## 七、什么时候**不要**用自动唤醒

| 情况 | 更合适 |
|---|---|
| 只需要"看一眼状态" | 一个**只读总览**入口（人主动看）即可 —— 别为它建任务 |
| 需要人做价值判断 | **停手请示**，别自动跑 |
| 高频短任务 | 直接**在当前会话做完** —— 唤醒的成本可能**大于**任务本身 |
| 对方会话**已经开着** | 直接在它那里说 —— **不必绕一圈** |

> **判断口径**：*这件事值得"叫醒一个会话"吗？*
> 如果它 30 秒能做完、却要花 2 分钟唤醒 + 一轮模型调用 —— **当前会话直接做完更划算**。
