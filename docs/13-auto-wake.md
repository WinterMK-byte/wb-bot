# 13 · 一句话派单与自动唤醒（Auto-Wake）

> **这一篇回答一个问题**：
> *我说一句话，系统能不能自己把活安排下去、还能让"没开着的会话"真的动起来？*
>
> **答案：能。** 但**必须先把两个事实搞清楚**，否则你会设计出一个"看起来自动、其实不动"的系统。
> 本文含**实测数据**（不只是设计）。

---

## 一、先破除一个幻觉：会话**不会**被唤醒

| 场景 | 能自动吗 |
|---|---|
| 你在**当前会话**说话 | ✅ 它立刻做 |
| 你希望**别的会话**也动 | ❌ **它没开着 = 没在跑**，听不到你说话 |
| **调度系统的任务触发** | ✅ **能自动跑**（不需要你开着任何会话） |

**关键区别**：
- 「会话」是**活的进程** —— 没开就是没在跑，**不可能"收到"任何东西**
- 「调度任务」是**系统级的定时器** —— 到点就**新建一个会话实例**去干活，**不需要你开着任何窗**

⇒ **所以"自动唤醒"的唯一可靠手段 = 调度系统的一次性任务。**

**推论（很重要）**：
- 只把单子写进"共享日志"、然后期待对方"看到" ⇒ **它看不到**，因为它可能压根没开着
- 想让它**真的动** ⇒ **投递 + 唤醒**，两件都要

---

## 二、破解：把"唤醒"当作派单的最后一步

```
你说：「让 X 组检查 Y」
        │
        ▼
【调度会话】立即执行四步：
   ① 写单           → 结构化文档（要素见 12 号文档 §五）
   ② 投递           → 收件箱 + 贴到 X 组工作区（双通道）
   ③ ★ 建一次性任务  → N 分钟后，在 X 组工作区触发：
        「读 <单子路径> 并执行；完成后按交接纪律回执」
   ④ 登记日志
        │
        ▼
【N 分钟后】X 组会话被**自动启动** → 读单 → 干活 → 回执
        │
        ▼
【调度会话】读到回执 → 报你结果
```

**这就是「一句话 → 自动安排 → 自动执行」。**

---

## 三、实测数据（真实跑过，不是设计）

**实验**：建一个一次性任务，让它在**调度会话之外**自动跑一次、写个文件证明它真启动了。

```text
建单    : 19:57:05
预定触发: 20:00:00
实际开始: 20:00:28      ← ★ 延迟 28 秒
完成    : 20:00:36
```

**三重证据**（★ 缺一不可 —— 单看一个都可能被"假象"骗）：

| 证据 | 内容 |
|---|---|
| ① **产物文件** | 生成了 `_wake_test.txt`，内容含真实时间戳 |
| ② **执行记录表** | `20:00:28 / status=ACCEPTED / result_success=1` |
| ③ **记录标题** | 「唤醒能力实测通过。已将当前本地时间写入…」 |

**关键**：**全程调度会话没做任何操作** —— 是任务让会话自己醒过来干的。

> **为什么强调三重证据**：只看文件 → 可能是别的东西写的；
> 只看记录 → 可能记录了但没真跑。**三者交叉才算证完。**（同 06 号教训）

### ★ 延迟特性（设计时必须知道）

**预定 20:00:00，实际 20:00:28 —— 约 30 秒延迟。**

⇒ **唤醒不是瞬时的**。
- 别指望"说完立刻动"
- **1–2 分钟的延迟是正常的**，不是故障
- 对用户的预期要按「**分钟级**」而不是「秒级」

---

## 四、两条路（推荐 A）

| | **A · 即时唤醒**（推荐） | B · 总管巡检 |
|---|---|---|
| 怎么触发 | 你说一句 → 调度会话**顺手建**唤醒 | 定时任务每隔 N 分钟**扫收件箱** |
| 精准度 | ★ **按需** —— 只唤醒该唤醒的 | 无差别扫，可能空跑 |
| 成本 | ★ **省**（有活才烧） | **费**（固定频率烧，哪怕没事） |
| 适合 | 日常 | 你希望**完全不开口**时的兜底 |

**推荐 A**：精准、省、可控。
**B 作兜底**：防止"你说了但调度会话没记"（但**B 会无差别烧钱**，慎开）。

---

## 五、代价与边界（**不可省**）

| 项 | 情况 |
|---|---|
| **成本** | 每次唤醒 = 目标会话跑一轮 ⇒ **产生一次模型调用开销**。**这是"自动"的代价** |
| **时段** | 唤醒时间必须落在**你的可用时段内**（本机铁律：**06:00–23:00**） |
| **可靠性** | ★ 被唤醒的**仍然是 agent** —— 它可能偷懒、跑偏、甚至说"做完了"却没做（见 12 号事故）。**所以回执 + 独立复核不能省** |
| **不能并跑** | 各会话**串行**（同一时刻只跑一个），**不存在真并行** |
| **硬限制** | ❌ **不能"让所有会话都醒着"** —— 既不可能（资源），也没必要（会乱）。**按需唤醒才是对的方向** |
| ★ **作用范围** | ❌ **只能唤醒「同一运行时」的会话** —— **跨运行时的执行方唤不醒**（见 §六） |

> ★ **最容易犯的错**：以为"自动唤醒"= "全自动无人管"。
> 它**只是把"手动打开会话"这一步自动化了** —— **判断、验收、纠偏仍然需要人**。

---

## 六、★ 作用范围：**只能唤醒"自己人"**（重要）

调度系统是**某个运行时自己的**。所以：

| 目标是 | 能唤醒吗 | 说明 |
|---|---|---|
| **同一运行时**的会话 | ✅ **能** | 调度器给该工作区新建一个会话实例 |
| **另一个运行时**的执行方 | ❌ **不能** | 两个是**独立产品**，`automation` 管不到对方 |

**跨运行时唯一的公共面 = 共享文件系统。**

⇒ 跨运行时派单的完整图景：

```
出单方判断该谁做
  ├─→ 同一运行时的会话  → 写单 + 投递 + ★ 唤醒     ✅ 全自动
  └─→ 另一个运行时的执行方 → 写单 + 投递             ⚠️ 唤不醒
                              ↓ 只能靠：
                                a) 人手动打开对方会话
                                b) 对方运行时自己的调度（如果有）
                                c) 中间层转达（但中间层同样唤不醒它，只能写单）
```

**一句话**：

> **能"叫醒"的是自己运行时的人手；跨运行时的执行方只能"留言"，不能"叫醒"。**

### 对派单纪律的影响（很实际）

| 派给谁 | 投递之后 |
|---|---|
| **同一运行时** | 可以要求「**限时回执**」—— 因为你叫得醒它 |
| **另一个运行时** | ★ **不能假设它会自己开工** ⇒ 投递后**必须告诉人**：「这张单需要你在那边开一下会话」 |

> ⚠️ 否则就是 **[12 号文档](12-handoff-discipline.md) 里那个"派了没人知道"的老毛病** ——
> 换了个地方原样重演。

---

## 七、★ 模型选择：**不要一律用同一个模型**

**踩过的坑**：为了让任务"统一"，把所有任务都设成同一个模型 ——
结果**简单任务浪费、复杂任务不够用**。

**分档原则**：

| 任务性质 | 模型档位 | 例 |
|---|---|---|
| **机械**：读文件 / 跑脚本 / 登记 / 汇报 | **轻量快模型** | 定时巡检、状态汇总 |
| **需要判断 / 写长文档 / 长上下文** | **强模型** | 出方案、写报告、跨文件分析 |

**两个必须知道的坑**：

1. ★ **不指定模型 ≠ 用你想要的模型** —— 会用「**建任务的那个会话**」的当前模型。
   实测：建单会话用的是 A 模型，建出来的任务就是 A，**哪怕你心里想的是 B**。
2. ★ **"ID 能写进库" ≠ "功能按那个 ID 生效"** ——
   有的平台存在**不在用户可选清单里的内部 ID**（能跑、但不在选项里）。
   ⇒ **真要确认，得看实际执行记录，不是看配置字段**（同 06 号教训）。

> **判断口径**：*这个任务错了会怎样？* 会写错东西 → **用强模型**；只是汇报状态 → 轻量就够。

## 八、落地检查清单（照做即可）

- [ ] 投递**落到对方启动必读的位置**（不是只写日志）
- [ ] 唤醒任务**建在目标工作区**（`cwd` 必须是那个工作区）
- [ ] 任务 prompt **自包含**：单子路径 + "做完按交接纪律回执"
- [ ] 指定**模型**（★ 别默认 —— 不指定会用「建任务会话」的当前模型，**可能与预期不符**）
- [ ] ★ 确认目标是**同一运行时**（跨运行时唤不醒 —— 只能投递 + 告诉人）
- [ ] 触发时间**落在允许时段内**
- [ ] 延迟按 **1–2 分钟**预估
- [ ] ★ 完成后**出单方独立复核**（不看回执看实测）

---

## 九、什么时候**不要**用自动唤醒

| 情况 | 更合适 |
|---|---|
| 只需要"看一眼状态" | 一个**只读总览**入口（人主动看）即可 —— 别为它建任务 |
| 需要人做价值判断 | **停手请示**，别自动跑 |
| 高频短任务 | 直接**在当前会话做完** —— 唤醒的成本可能**大于**任务本身 |
| 对方会话**已经开着** | 直接在它那里说 —— **不必绕一圈** |

> **判断口径**：*这件事值得"叫醒一个会话"吗？*
> 如果它 30 秒能做完、却要花 2 分钟唤醒 + 一轮模型调用 —— **当前会话直接做完更划算**。
