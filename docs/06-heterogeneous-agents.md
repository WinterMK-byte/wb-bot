# 06 · 异构 Agent 之间的协作

> 前面的文档讲的是**一个 Agent 内部多个会话**怎么共享一条总线。
> 这一篇讲更难的一层：**两个完全不同的 Agent 运行时**之间怎么协作。

---

## 一、问题的真实形状

现实里，一台机器上跑着不止一个 Agent，而且它们**往往不是同一家的产品**：

| | **常驻型 Agent** | **会话型 Agent** |
|---|---|---|
| 形态 | 桌面应用，开机即活，后台长驻 | 按需开启，一次对话一段上下文 |
| 记忆 | 自带数据库，跨天累积 | 每次基本从零开始 |
| 强项 | 操作本机（桌面 / 浏览器 / 系统 / 长任务 / 定时 / 值守） | 深度研究、大文档生产、代码工程、第二视角判断 |
| **对外接口** | **常常没有 API** —— 你只能读它的**文件系统痕迹** | 有 API，但你不一定想让它长连 |
| 谁能改它 | 它自己 | 它自己 |

**决定性约束**：常驻型 Agent **不向你暴露 API**。

于是"实时推送""消息队列""webhook""gRPC" 这些常规手段**全部出局** ——
它们都要求至少一侧能被对方主动调用。

> **不能推送，就只能"定期看它在磁盘上留下了什么"。**

这不是退而求其次。这是一个**结构性事实**，绕不过去，只能承认它、然后在它之上设计。

---

## 二、解法：单一总线 + 水位线

```
   常驻型 Agent                        会话型 Agent
        │                                   │
        │ 写（只能靠它自己写）                 │ 写（走工具）
        ▼                                   ▼
   ┌─────────────────────────────────────────────┐
   │        单一权威总线（append-only 日志）        │
   │        一个文件。唯一写入入口。                │
   └─────────────────────────────────────────────┘
                       │
                       │ 读：按 ID 水位线，只取增量
                       ▼
                 消费方（谁都可以）
```

三个设计选择，每个都有理由：

### 1. 用**文件**当中介，不用网络

因为唯一的共同语言就是文件系统。
总线必须是**人可读、机可解析、可 `git diff`、断电不丢**的纯文本 —— 这就是 markdown 表格而不是 SQLite 或消息队列的原因。

### 2. 用**水位线**做增量，不做事件订阅

消费方记住"我上次读到 ID=342"，下次只处理 >342 的行。
不需要常驻监听、不需要长连接、不需要对方配合。

**水位线是加速器，不是过滤器** —— 冷启动或换了消费方时，必须能全量重读。
只信水位线会导致"新来的 Agent 看不到历史"（见 [教训 05](lessons.md#05-只读镜像--信息孤岛)）。

### 3. **单一**总线，不搞"每对 Agent 一条专属通道"

`N` 个 Agent 两两建通道是 `N²` 条；一条公共总线是 `1` 条。
且公共总线上每条都写清了"来源 / 做了什么 / 需要谁" —— **任何一方都能只看自己关心的列**，等于免费得到过滤。

## 三、怎么切分工：按"生成 vs 操作"，不按领域

最容易犯的错是**按业务领域分**（"你管数学，我管英语"）。这会在第一次交叉任务时崩掉。

正确的切法是按**动作性质**：

| 维度 | 常驻型 | 会话型 |
|---|---|---|
| 擅长 | **跑**：让本机某个东西的状态发生变化 | **产**：产出一段话、一份文档、一张图、一个判断 |
| 产出 | 执行结果 + 运行证据 | 结论 + 产物 |
| 判断权 | "在本机把它做出来" | "这么做对不对 / 哪个方案好" |

一条完整链路的形状：

```
会话型出方案/产物  →  常驻型落地执行/盯运行  →  会话型回收数据出下一版
```

**判据（拿不准时用）**：
- 产出是**一段话 / 一份文档 / 一张图 / 一个判断** → 归会话型
- 产出是**本机上某个东西的状态变了**（文件移动、服务启动、界面被点、进程被杀）→ 归常驻型
- 两者都要（"分析磁盘占用并清理"）→ **会话型出清单，常驻型执行**

## 四、主导权：能力分工 ≠ 权限归属

能力分工是"谁擅长什么"，**权限归属是"谁说了算"**。这两件事必须分开定义，否则会长期扯皮。

一条经过验证的落地方式：

| 项 | 常驻型 | 会话型 |
|---|---|---|
| 定位 | **受托方**：只读资料源 + 代跑执行器 | **主导方** |
| 行为约束 | 不新起任务、不主动推进、不并行维护第二版产物 | 出方案、派活、验收 |
| 写权限 | **可以写**（必要时），但**必须登记四要素并等复核** | 写 + 复核 |

> **关键**：不要用"能不能写文件"来划边界 —— 那是能力问题。
> 要用"**写完谁复核**"来划 —— 那才是权责问题。

**四要素登记**（任何一方动了共享资产都必须写）：

```
改了什么  | 为什么  | 影响面  | 回滚点
```

## 五、交接件的五种类型

跨 Agent 的沟通**必须落盘**（因为一方读不到另一方的对话）。实践中沉淀出五种：

| 类型 | 用途 | 生命周期 |
|---|---|---|
| **协作卡** | 双方都读的唯一协议 + 资产索引 | 长期，只追加 |
| **契约** | 特定边界（"A 管这个、B 管那个"）的书面约定 | 长期，版本化 |
| **派单 / 施工单** | 把一件事交给对方做，含验收标准 | 一次性 |
| **复核报告** | 对派单结果的独立验证 | 一次性 |
| **通知** | 告知（不需要对方行动） | 一次性 |

**纪律**：全部**只追加、不改历史行**。
改历史 = 让另一方基于旧数据做判断 = 静默事故。

## 六、踩过的坑

### 6.1 新会话"听不懂人话"

老板说一句口语（"那个东西弄一下"），新开的会话完全不知道该干什么 ——
因为它缺一张「**这句话归谁、用哪个现成资产**」的映射表。

→ 解法是**路由卡**，见 [08 · 路由层](08-routing.md)。

### 6.2 隔离的 Agent 不会报错，只会给偏的方案

如果给 Agent 读的是**只读镜像**，而镜像不会自动同步 ——
那么它看到的可能是**五天前的世界**，并且**它自己不知道**。

它会基于过时信息认真给出一个方向错误的方案，**全程不报任何错**。

→ 见 [教训 05](lessons.md#05-只读镜像--信息孤岛)。隔离本身不是问题，**"隔离且不知道自己在隔离"才是**。

### 6.3 给 Agent 的说明书里写死了会过期的前提

如果给某 Agent 的引导文件里写着"本项目 X 月 X 日就结束了，别做长期资产" ——
而实际上项目被续期了 —— **它会基于一个错误的自我认知去规划**（只提能短期收尾的方案）。

→ 给 Agent 的每一份"前提说明"都要**带日期**，并在前提变化时**主动重写**。

## 七、这套东西和单机多会话的关系

| | [02 · 架构](02-architecture.md) | 本篇 |
|---|---|---|
| 覆盖 | 一个运行时内的多会话 | **多个运行时之间的** |
| 共享 | 总线、席位、锁 | 再加：能力边界、主导权、交接件 |
| 复用 | 同为**单一权威总线**，同一套写入纪律 | |

**总线是共用的**。这是这套设计最省的地方 ——
不管是一台机器上的多个会话，还是跨越不同厂商的两个 Agent，**都往同一条总线写**。
