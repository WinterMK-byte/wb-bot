# 10 · 跨进程资源租约（平台绑定案例）

> ⚠️ **本篇是"平台绑定案例"，不是通用规范。**
> 场景是 **Windows + NVIDIA 单卡**（本机 8 GB 显存）。
> 但它要解决的问题 —— **多个互不知情的进程抢占同一份稀缺资源** —— 是通用的。
> 换成其他独占资源（端口段 / 数据库连接池 / 独占文件锁），三层结构和判定方法可整体迁移。

---

## 一、问题

一台机器上跑了几个**互相独立**的 AI/模型服务：

```
服务 A（本地对话 + 向量检索）  占 ~6.8 GB
服务 B（图像生成）            占 ~7.1 GB
服务 C（语音）                占 ~2.6 GB
游戏 / 剪辑                   不确定性占用
```

**8 GB 的卡，A + B = 13.9 GB，必然爆。**

现状是各组启动脚本**互不知情**：

| 痛点 | 后果 |
|---|---|
| 后启动的把显存挤爆 | 先跑的**崩在半路**，且报的是 OOM 不是"被挤死了" |
| 想互斥只能"杀进程" | 按名字杀**解释器进程**会**误杀探针自己**（多个服务同用一个解释器） |
| 没有"谁在占"的共识 | 没人知道某端口是 A 还是 B |
| 用户不在旁边时 | **静默杀 = 用户的活被无声中断** |

> 核心诉求一句话：**把"谁在占资源"变成一张可协商的租约表 —— 跑前领租约、冲突不静默杀、请示人。**

---

## 二、三层架构

```
 L1 · 组清单（静态声明，一个 JSON）
   ├─ 每组自述：name / need_mib / ports / models / probe / release
   └─ 声明式：新组接入 = 加一段 JSON，不改一行代码
        │
        ▼
 L2 · 租约（动态状态，一个 JSON）
   └─ { group, pid, started, heartbeat, ttl_s, need_mib, ports, models }
        │
        ▼
 L3 · 协商（冲突处置）
   ├─ 默认：打印请示 + 退出码 5（不 kill）
   ├─ --force-others：关掉对方后继续（仍排除自己）
   ├─ --yield：搁置本任务（零副作用）
   └─ --ask：弹窗问人，超时按搁置
```

### 设计原则

| 原则 | 落实 |
|---|---|
| **零常驻** | 全部是一次性 CLI / 库调用，**不装守护进程** |
| **声明式** | 新组接入只加 JSON |
| **不猜** | 一切以实测为准（`nvidia-smi` + `netstat` + 服务自己的 `/api/ps`） |
| **可审计** | 每个关键动作写 append-only JSONL 事件流 |
| **失败即停** | 资源不够就停手，**绝不硬跑** |

### 关键概念：**"组" ≠ "应用"**

这是最容易搞错的地方。

```
组 = 共用同一份资源的单位
```

如果三个服务（本地对话 / 文档检索 / 某个工具）**共用同一个模型服务 + 同一份模型权重**，
它们是**一个组**，组内**不互斥**（只是并发请求）。
把它们当成三个组 → 会自己跟自己抢。

## 三、★ 核心洞察：活跃判定必须"双轨"

**这是上线第一天就会暴露、且不修就完全失效的一条。**

朴素做法：**只看租约** —— 租约文件里有这条记录、进程还活着 → 判定为"活跃"。

**为什么错**：

> **用户双击图标启动的服务，不会自己登记租约。**

实测：某个服务占了 6.5 GB 显存，而租约文件是**空的** —— 因为它是被手动启动的，根本没走过 `acquire()`。
如果只认租约 → 系统**看不见它** → 算账时以为资源空闲 → 启动新组 → 爆。

**正确做法：两轨取并集**

```
活跃 = 租约轨 ∨ 实测轨

  租约轨：租约记录存在 ∧ pid 存活 ∧ 心跳未超时
  实测轨：真去查（端口在听？进程在？服务自己的状态接口有驻留模型？）
```

| 轨 | 覆盖 | 局限 |
|---|---|---|
| 租约轨 | 走过 `acquire()` 的（正常流程） | 看不见手动启动的 |
| 实测轨 | **所有实际占用的**（无论怎么启动的） | 有查询开销；需按组声明查询方式 |

**教训一句话**：*任何"只记录自己做的事"的设备，都会漏掉用户手动做的事。*

## 四、退出码语义（调用方靠它决策）

| 码 | 含义 | 调用方该做什么 |
|---|---|---|
| `0` | 成功拿到租约 | 继续跑 |
| `5` | **有冲突，待裁定** | **停手，请示人**（不是错误，是"需要决策"） |
| `6` | 抢到了但**资源仍不足** | **停手，不硬跑** |

**为什么把"冲突"做成正常退出码而不是异常**：
冲突是**预期的、需要人决策的状态**，不是 bug。
用独立退出码让它可编程处理（调用方可以"看到 5 就弹窗问人"），而不是被当成崩溃。

## 五、三个"只有真机才暴露"的坑

### 5.1 `0` 是假值

```python
code = int(code or EXIT_INTERNAL)   # ← BUG：code=0（成功）被 or 吃掉，变成"内部错误"
```

**形态**：成功路径返回 0，但 `0 or DEFAULT` = `DEFAULT` → **成功被误判成失败**。

→ 修法：显式判 `is None`，不要用 `or` 兜底数字。

### 5.2 资源"卸载"是异步的

调用 `保持不占用` 之后，资源**不会立刻**回收。
实测：某次卸载 6474 MiB，1.2 秒后只回收了 2161 MiB。

→ **判"够不够"必须轮询**，不能卸载后立刻算账。否则会误判"资源已释放"而放行。

### 5.3 不同接口走不同端点

同一个服务，**生成类**和**嵌入类**请求走**不同的 HTTP 端点**。
拿生成端点去查嵌入模型的状态 → 400。

→ 探针必须**按模型类型选端点**，不能一个端点打天下。

---

## 六、红线（绝不越界的两条）

### 6.1 绝不 kill 宿主进程本体

只通知它**卸载模型**（`keep_alive=0` 之类），**绝不 kill 那个常驻服务的进程**。
因为：
- 进程本体可能还承载着别的东西
- 杀掉后用户下次得重新启动

### 6.2 某些资源永久豁免

有些端口/进程**看起来在占资源，实际不参与显存**（或属于关键基础设施）。
把它们列进 `never_touch_ports` / `never_kill_procs`，
并在**代码里再硬编码一层保险** —— 配置可能被人改错，代码常量不会。

> ⚠️ 关键是**判定要落在"实测"上**：某个进程"看起来像在占"不等于"真的在占"。
> 用实测（显存用量、端口在听）代替名字匹配。

## 七、声明式接入（新组怎么加）

新组接入**只需要在组清单 JSON 里加一段**，不动代码：

```json
{
  "my-group": {
    "need_mib": 3000,
    "ports": [XXXX],
    "models": ["model-name"],
    "probe": "port_listening",
    "release": "kill_ports"
  }
}
```

`probe` / `release` 是**受限词汇**（枚举），不是任意代码：

| `probe` 值 | 语义 |
|---|---|
| `port_listening` | 端口里有任一在 LISTENING（最精确，最常用） |
| `service_resident` | 服务的状态接口报告有驻留模型 |
| `proc_alive` | 进程名里有任一存活 |
| `any` | 三者任一成立 |

| `release` 值 | 语义 |
|---|---|
| `kill_ports` | 按端口精确反查 PID → 终止（自动排除自己 + 保护名单 + 豁免端口） |
| `unload_models` | 列模型 → 逐个卸载（**绝不杀服务本体**） |
| `ask_manual` | 不动手，只打印"请手动退出" |
| `none` | 什么都不做 |

**为什么要枚举而不是让用户写脚本**：
声明式才能保证"托管方"能统一审计 —— 如果每组自己写"怎么释放"，就无法保证它不会误杀。

---

## 八、自测清单

```
① 组清单能解析，每组 probe/release 都是合法枚举          ← 拒绝拼错的词汇
② 空态下 acquire 成功，退出码 0
③ 已有租约时 acquire → 退出码 5（不 kill）
④ --yield 退出后，租约被清空、零副作用
⑤ 并发 acquire 同一组 → 只成功一个（不超卖）
⑥ 僵尸租约（pid 死 / 心跳超时）→ 可被抢占
⑦ 手动启动的组（无租约）→ 实测轨能发现它        ← 双轨判定的验收
⑧ 豁免端口/进程 → 任何路径都不碰
⑨ 资源不足 → 退出码 6，且租约已回滚
```

## 九、可迁移的形状

把"显存"换成别的独占资源，这套依然成立：

| 显存 | 可换成 |
|---|---|
| 组 = 共用同一模型的进程 | 组 = 共用同一数据库实例的服务 |
| 租约 = pid + 心跳 + TTL | 同 |
| 实测轨 = 查端口/显存/状态接口 | 实测轨 = 查连接数 / 锁持有 |
| 冲突 = 资源不够 | 冲突 = 端口占用 / 连接池耗尽 |
| 退出码 5/6 | 同 |

**不变的内核**：
1. 声明式组清单（新组不改代码）
2. 租约（有 TTL，僵尸可抢）
3. **双轨活跃判定**（租约 ∪ 实测）
4. 冲突**默认不杀，请示人**
5. 可审计事件流

> 这五条里，**第 3 条最容易被漏**，也最容易让整个系统从第一天就失效。
