# 07 · 席位治理

> 有了总线（[04](04-bus-protocol.md)）解决"日志怎么写不乱"，有了跨运行时通道（[06](06-heterogeneous-agents.md)）解决"两个 Agent 怎么通讯"。
> 这一篇解决最后一件、也是最贵的一件：**谁有权改什么**。

---

## 一、为什么需要"席位"

一个反直觉的事实：多 Agent 系统里**最大的成本不是算力，是越界**。

具体长这样：

- 协调方手一伸，直接改了某条业务线的核心脚本 → 那条线自己的负责人**不知道**，下次调试时基于一个已经被改过的世界
- 执行方"顺手"优化了别人的产物 → 两个版本并存，谁也不知道哪个是最终版
- 两边都以为对方在做 → **同一件事做了两遍**，或者**谁都没做**

这些事故的共性：**没有一条"这事归谁"的权威判据**。每个人（每个 Agent）都在凭记忆猜。

> 所以"席位"不是权力游戏，是**降低协调成本的基础设施**。

---

## 二、三层席位模型

一个够用的模型只需要三层：

| 层 | 席位 | 管什么 | 数量 |
|---|---|---|---|
| **架构层** | 协调者 | 架构设计 / 方案把关 / 跨线排期 / 验收 / 仲裁 | 全机 **1** 个 |
| **业务层** | 各线负责人 | 该线的判断 / 方案 / 产物 / 质检 | **每条线 1 个** |
| **执行层** | 执行者 | 跑腿 / 常驻运维 / 长任务 | **每条线 1 个** |

```
              协调者（1）
             ╱    │    ╲
     线A负责人   线B负责人   线C负责人
        │          │          │
     执行者A    执行者B    执行者C
```

**每条线 = 1 个负责人 + 1 个执行者**。这个比例是有原因的：
负责人管"想"（出判断、出产物），执行者管"干"（让本机状态变化）。
两者**职责不同、寿命不同** —— 执行者需要不断迁移（换机器/换环境），负责人不需要。

### 一个反例：没人管 ≠ 需要一条线

不要因为"这件事现在没人管"就新开一条线。新开一条线的判据是**三条同时满足**：

1. 有持续迭代需求
2. 有独立产物
3. 每周至少动一次

否则 → **归协调者代管**。

## 三、边界判据：动手前的一句话自检

**任何 Agent 在改任何文件之前，先问自己：**

> **「我要改的这个文件，属于哪条线？」**

- 属于某条线 → **停手，转给该线负责人**
- 属于协调层 / 本机全局 → 可以直接做

这一句话能挡掉绝大多数越界。它的价值在于**可机械执行** —— 不需要判断力，只需要一次归属查询。

配套的归属表（谁是负责人）必须**有唯一真源**（见 [08 · 路由层](08-routing.md)），
否则"属于哪条线"这个问题本身就会引发争论。

### 越界的典型形状（泛化后）

| 越界动作 | 本该谁做 |
|---|---|
| 协调方直接改了某线的核心脚本（加盐值、改参数） | 该线负责人 |
| 协调方直接改了某线的评测集口径 | 该线负责人 |
| 协调方改了执行方所在平台的配置文件 | 执行方（经该线负责人） |

**注意**：改配置文件、改参数、改 prompt —— 这些**看起来是小事，但都是"核心资产"**。
判断标准不是"改动量大小"，而是"**这个改动会不会改变那条线的产出**"。

---

## 四、柔性条款：越界禁令不能变成推诿

纯粹的"不越界"会走到另一个极端：**任何事都要跨会话转发一轮**，而转发本身有成本（重启上下文、手动搬运、一轮往返）。

所以需要一条柔性条款：

| 情况 | 动作 |
|---|---|
| **默认**：会动到别人的线 | 转给该线负责人 |
| **可代劳**：切换成本明显高于直接做 | 协调者**直接做**，但要报备 |

**什么叫"切换成本明显更高"**（四个典型）：

1. 一条命令就能改完的小事
2. 对方正在等结果，走一轮往返明显更慢
3. 只是"顺手报备"性质
4. 改的是**跨线共享的小接口**

### 代劳后三件套（缺一不可）

代劳不是"先斩后奏"，而是"**做了但留下完整痕迹**"：

1. **当场点明** —— 在回复里明确说"这次我代劳了 + 为什么"（让owner知情）
2. **登记** —— 写进总线（四要素：改了什么 / 为什么 / 影响面 / 回滚点）
3. **通报** —— 涉及该线资产的，事后通报该线负责人

**判断口径（一句话）**：

> *这件事的下一步，是「转给别人」还是「我 5 分钟就能收尾」？* —— 后者 → **代劳 + 报备**。

### 仍不可代劳的部分

无论切换成本多高，**业务线的核心资产**必须经该线负责人：

- 代码主逻辑
- 评测集口径
- 算法参数
- 产物的最终版本

因为这几样一旦被外部改动，**那条线就不再"自己拥有"自己的正确性标准**了。

## 五、治理规则本身怎么改

规则会变（席位改名、边界调整、新线成立）。改规则时有两个硬要求：

### 5.1 只追加，不改历史

和总线同一条纪律。改历史 = 让后加入的 Agent 基于错误历史理解现状。
正确做法：**文末追加新版本节，并更新顶部的"现行版本"指针**。

### 5.2 区分"改定义"和"改归属"

| 改什么 | 要不要同步别处 |
|---|---|
| 改**席位定义**（三层模型、职责描述） | **必须**同步所有"注入点" |
| 只改**某资产的归属**（这个文件从 A 归到 B） | **不必**同步定义 |

"注入点"是什么？见 [05 · 通知注入](05-injection.md) ——
凡是**每个 Agent 启动时会读**的地方（身份文件、启动脚本、引导文档），都是注入点。

> 关键判据：**不是"相关"就加注入点，而是"不写进这里，某个 Agent 就真的不知道"才加。**

---

### 5.3 条件性「取消中间层」—— 用判据，不用感觉

**主张**：如果执行方能**完全按单执行**，那么**中间层（协调 / 质检席位）可以撤掉** —— 直派即可。

**这个主张成立，但必须带条件。**
否则会在执行方掉链子时**同时失去两层保护**（没人派好单 + 没人复核）。

**判据（四条，同时满足才算成立）**：

| # | 判据 | 怎么验 |
|---|---|---|
| 1 | 接单有**收到确认** | 日志有对应条目 |
| 2 | 执行有**回执**（逐条对照 + 一行验证命令的**实际输出**） | 同上 |
| 3 | **不做也回**（显式写「未做 + 原因」） | 同上 |
| 4 | **连续 ≥3 次**全部满足 1–3，且**出单方独立复核通过** | 去机器**实跑** |

> **为什么要求"连续 ≥3 次"**：单次成功可能是运气；**能连续，才是能力**。

**判据不满足时**：中间层**保留**，但**定位要改** ——
从「替执行方做判断」改为「**维护执行方的运行环境 + 必要时做规划**」。
（即：中间层不再"**过手**"，而是"**保底**"。）

**这个设计的好处**：撤掉中间层**不再是一次性豪赌**，而是一条
**可量化、可复核、可随时回退**的路径 —— 达标就撤，掉链子就回来。

> ⚠️ **反过来也要防**：别因为"执行方看起来挺靠谱"就提前撤 ——
> 「看起来靠谱」不是判据，**「连续 3 次可验证的回执」才是**。（对照 06 号教训）

## 六、踩过的坑

### 6.1 写进注册表 ≠ 通知到位

规则改了，写进注册表了 —— **但实际上没有任何 Agent 会去读注册表**。
结果：实际行为一点没变，而文档上写着"已更正"。

→ 这正是 [05 · 通知注入](05-injection.md) 和 [教训 09](lessons.md#09-写进文件--通知到位) 要解决的事：
**通知需要有"载体"（每个 Agent 启动必定读到的地方），文档只提供"可查证"。**

### 6.2 席位名被历史会话"劫持"

如果某一层席位改过名（比如从"X"改叫"Y"），
那么**历史会话里留下的旧署名**就成了误认来源 —— 后来者会拿旧署名推断现在的身份。

→ 席位沿革必须**显式记录**："某某历史会话都曾署名 X，别再据此认人"。

### 6.3 边界模糊的第三种情况

有些文件既不完全属于某条线，也不属于协调层（比如"某线目录下的运维脚本"）。
这种情况**不要硬判** —— 走柔性条款：**代劳 + 报备**，并在报备里点明"边界模糊，请 owner 确认归属"。
