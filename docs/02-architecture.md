# 02 · 架构

> 三层：**席位**定边界，**总线**存事实，**注入点**做通知。
> 每层只解决一件事，互不替代。

---

## 全图

```
┌─────────────────────────────────────────────────────────┐
│  注入点（injection points）                              │
│  每次启动都会读的位置 —— 通知唯一有效的载体              │
│  ┌───────────────────────────────────────────────────┐  │
│  │  席位（seats）                                     │  │
│  │  谁做什么、边界在哪、越界怎么判                    │  │
│  │  ┌─────────────────────────────────────────────┐  │  │
│  │  │  总线（bus）                                 │  │  │
│  │  │  单一权威 · append-only · 原子锁 · 写后自检  │  │  │
│  │  └─────────────────────────────────────────────┘  │  │
│  └───────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────┘
```

由内向外依赖：**总线**是最底层的事实来源，**席位**基于它追溯责任，**注入点**把规则送到每个 Agent 面前。

---

## 第一层 · 总线：唯一的事实来源

**它是什么**：一份 append-only 的结构化日志。每次交接、每次改动、每个断点，都往里追加一条。

**它不是什么**：
- ❌ 不是聊天记录（每条都要有明确字段）
- ❌ 不是任务列表（它记录"发生过什么"，不管理"要做什么"）
- ❌ 不是数据库（它就是一个人可读的 Markdown 表格 —— 这刻意的）

**为什么刻意做成 Markdown**：

| 好处 | 说明 |
|---|---|
| 人可直接读 | 出问题时不需要先写查询语句 |
| 可 diff | 版本控制天然可用，改动一目了然 |
| 零依赖 | 任何语言、任何工具都能解析 |
| 易迁移 | 换个系统，复制文件即可 |

代价是**必须自己维护一致性** —— 这正是 `wbb.bus` 存在的理由。

**四条不变量**（详见 [`04-bus-protocol.md`](04-bus-protocol.md)）：

1. 唯一写入入口 `append()`
2. ID 在临界区内计算
3. 写后自检，不合格自动回滚
4. 插入点用结构锚，不用"最后一个数据行"

## 第二层 · 席位：把边界写下来

**为什么需要**：任务在"谁该做"上撞车，损失往往大于任务本身。

**席位的三个要素**：

| 要素 | 回答的问题 |
|---|---|
| **职责** | 这个位置产出什么 |
| **边界判据** | 什么情况归我、什么情况必须转交 |
| **越界后果** | 越界了怎么发现、怎么补救 |

**关键设计**：席位不是"层级"，而是**职责切面**。
同一个 Agent 可以在不同任务里处于不同席位 —— 重要的是"这次我在哪个位置"。

详见 [`03-seats.md`](03-seats.md)。

## 第三层 · 注入点：让通知真的到达

**核心命题**：

> **"写进文件"和"通知到位"是两件事。**

一份写了但没人读的规则，等价于不存在。而且它更危险 ——
因为**你会以为它生效了**。

**判断标准只有一个**：*对方会自己读到吗？*

只有"每次启动都会自动进入上下文"的位置才算注入点。
其余都只是"可查证"（需要主动去翻）。

详见 [`05-injection.md`](05-injection.md)。

## 三层怎么协作：一次完整交接

```
1. Agent A 决定派活
   └─ 读总线（拿水位线，看自己错过什么）

2. Agent A 写总线
   └─ append(source=A, what="派了 T01 给 B", need="B")
      ← 唯一入口；写后自检；拿到真实 ID

3. Agent B 开工前
   └─ 读总线（since=自己上次的水位线）
      ← 发现 need="B" 的条目

4. Agent B 干活、写总线
   └─ append(source=B, what="T01 完成，12 个断言通过", artifact="out/t01.log")

5. 任何人可随时体检
   └─ verify() → ID 唯一 / 时间列合规 / 行序单调
```

**注意第 1 步和第 3 步**：两端都**先读再动**。
这是"总线模式"与"消息模式"的关键差别 ——
消息模式里，错过就是错过；总线模式里，**水位线让你能补上**。

## 与"多 Bot 群聊"类方案的区别

有一类方案是让多个 Agent 在一个"群聊"里实时对话、互相 @。
那解决的是**即时协商**问题，很有价值，但与本项目是**互补**而非替代：

| | 群聊式 | 本项目 |
|---|---|---|
| 解决 | 实时协商、即时分工 | 记录一致性、边界、事后可追溯 |
| 失效点 | 上下文膨胀、成本线性增长 | 一致性维护需要纪律 |
| 适合 | 短周期、高交互 | 长周期、多线并行、需要审计 |

**本项目不调度模型、不管上下文。** 它是一层**纪律**，可以叠在任意 Agent 运行时之上。

## 设计取舍记录

| 取舍 | 选了什么 | 为什么 |
|---|---|---|
| 存储格式 | Markdown 表格 | 人可读 > 机器效率（规模上限靠归档解决） |
| 一致性 | 自己实现（锁 + 自检） | 零依赖 > 复用现成库 |
| 通知 | 注入点清单（人工维护） | 显式 > 隐式（隐式通知一旦失效无人察觉） |
| 判据 | 宁少勿滥 | 信噪比 > 覆盖率（见教训 06） |
| 归档 | 默认只预演 | 安全 > 方便 |
