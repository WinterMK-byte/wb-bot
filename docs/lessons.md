# 教训库

> 这里每一条都对应**一次真实事故**：有现场、有根因、有"判据最后改成了什么"。
>
> 收在这里的原因只有一个 —— **机制可以被抄走，教训不能。**
> 你照着别人的 schema 建一份总线，三周后大概率会踩到其中一半。

## 01 · ID 撞号：分步读写的窗口期

**症状**：总线上出现两条 ID 相同的记录。不报错，只是某天统计时发现"条数对不上"。

**现场**：两个会话几乎同时往同一个文件追加。

```
A: 读文件 → max(id)=41 → 准备写 #42
B: 读文件 → max(id)=41 → 准备写 #42      ← 两者看到的是同一份快照
A: 写入 #42
B: 写入 #42                               ← 撞号
```

**根因**：`max(id)+1` 这个计算与"写回文件"之间隔着一个窗口。窗口里另一个进程也在算。
**只要这两步不是原子的，撞号就只是时间问题** —— 并发量越小，出现得越晚，越容易以为是别的原因。

**判据怎么改**：把「读 ID → 算插入点 → 写回」**整段**放进一把原子锁。

```python
fd = os.open(lockpath, os.O_CREAT | os.O_EXCL | os.O_WRONLY)   # 原子建档当互斥量
try:
    new_id = self.next_id()        # 在锁内算
    write(...)                     # 在锁内写
finally:
    os.remove(lockpath)
```

`O_CREAT|O_EXCL` 的价值在于：**"检查存在"和"创建"是同一个系统调用**，不存在窗口。

**可复用规则**
- 只要涉及"读-改-写"，先问一句：**这三步是一个原子操作吗？**
- 文件锁要带**陈旧清理**（持有者崩溃时锁不会自己消失）。
- **不要用"文件存在与否"当锁**，除非那个"存在"是原子创建的。

## 02 · 插入锚被正文劫持：修工具的注释，给工具埋了雷

**症状**：新条目被插进**表格中段**，物理最后一行反而是条旧记录。行序检查偶尔报错，但复现不了。

**现场**：判断"新行插哪"的代码是这样的 ——

```python
for i, line in enumerate(lines):
    if line.strip().startswith("## 变更记录"):     # ← 宽松匹配
        tail_hdr = i
        break
# 再往上找最近的一条 --- 当插入点
```

看起来没问题：找"变更记录"标题，插在它前面。

**根因**：某条历史记录的**正文里有一行**，恰好以 `## 变更记录` 开头。

```
| 88 | 2025-06-11 | ... | 说明：这条记录的插入点计算方式，
## 变更记录 之前的第一条分隔线，是这样的 ...
```

于是 `tail_hdr` 落在了**表格中段**，而真正的标题在**文件很靠后的位置**。
插入点被拽到表格中间 → 新行插进老条目之间。

**最讽刺的一点**：那行正文，是**上一次修复这个功能时写下的说明文字**。
修 bug 的注释，给同一个 bug 埋了下一颗雷。

**判据怎么改**：要求它是**独立的标题行** —— 行首 `##`，**且行尾没有别的内容**。

```python
if re.match(r"^##\s+变更记录\s*$", line.strip()):   # 行尾必须是结束
```

**可复用规则**
- **结构化匹配一律用锚定正则**（`^...$`），别用 `startswith` / `in`。
- 凡是"在自由文本里找结构标记"的地方，都要假设**正文里会出现同名串**。
- 修一个解析 bug 时，先问：**我写进数据的这段说明，会被同一个解析器误读吗？**
- 判据的严格程度要与"数据的自由度"匹配 —— 内容越自由，判据越要锚定。

## 03 · 手写行 vs 工具行：怎么一眼认出"有人绕过了工具"

**症状**：ID 撞号查不出原因 —— 锁是好的，代码是对的，可就是有重号。

**现场**：总线头部写着"**ID 递增，写之前先看最后一行的 ID，+1**"。
而工具内部用的是 `max(id) + 1`。

**两者口径不一致**。只要表格里有多行条目、行序不完美，"看最后一行"就会算出**已经用过的 ID**。

**根因**：**存在第二条写入路径** —— 有人直接编辑文件，绕过了锁和插入点计算。
锁再严也没用，因为对方根本没走锁。

**判据**：找出**只有工具才会留下的痕迹**。

工具生成的时间列是 `YYYY-MM-DD HH:MM`；手写的人通常只写日期：

```
| 57 | 2025-08-02 | ...        ← 没有时分 → 手写行
| 58 | 2025-08-19 21:0x | ...  ← 占位符 → 手写行
```

于是体检里加一条：

```python
RE_TIMESTAMP = re.compile(r"^\d{4}-\d{2}-\d{2}\s+\d{2}:\d{2}")
if not RE_TIMESTAMP.match(cell_time):
    problems.append("时间列不合规 —— 疑似绕过工具手写的行")
```

**可复用规则**
- 存在"绕过工具"的可能时，**在数据里留一个工具专属指纹**，并把它写进体检。
- 光禁止绕行不够，**要能检测出发生了绕行**。
- 发现第二条写入路径后，先做两件事：① 把它封掉（文档明写"唯一入口"）② 加检测。

## 04 · 写死的绝对路径：迁移后必然静默失效

**症状**：某个例行任务几个月来一直"正常执行"，但产出永远是空的。

**现场**：任务的提示词里写死了一个绝对路径：

```
读取 …\Desktop\old-plan.md，推一份当天的执行清单
```

而这份文件早在一次重构里被换掉、迁到了新目录。旧路径**不存在**。

**根因**：任务**不会因为"文件不存在"而失败** —— 它会照常跑完，然后老老实实报告
"文件不存在，无法给出安排"或者干脆给出一个空清单。**没有任何人会去看那份清单。**

**判据怎么改**：盘点时把「提示词里所有绝对路径」**逐条 `exists` 验证**，
这是固定动作，不是"顺手看看"。

```python
for label, p in hardcoded_paths:
    print(label, "✅" if os.path.exists(p) else "❌ 缺失", p)
```

**可复用规则**
- **配置里的路径是硬编码时，它就是一个定时炸弹**，倒计时从"下次重构"开始。
- 判断一个自动化"是否健康"，不能只看它**有没有报错** —— 要验它的**产物有没有内容**。
- 迁移/重构的收尾清单里，必须有一项：**扫描所有写死路径的使用方**。

## 05 · 只读镜像 = 信息孤岛

**症状**：一个被隔离的 Agent 给出了一份很认真、但**方向完全偏了**的方案。

**现场**：出于安全，给这个 Agent 划了个工作区，规则明写
"**禁止读写主目录**，需要的东西都在 `_inbox/` 里有副本"。
而 `_inbox/` 是**手动镜像**，没有自动同步机制。

实测：镜像停在 5 天前，而权威源已经更新了十几版。
这 5 天里新增的关键架构文档、修订过的规则表，它**一份都没看到**。

**根因**：**"隔离"和"信息新鲜度"是有冲突的**，而没人去调和它 ——
隔离规则写得很硬（禁止读原件），镜像刷新却完全没有机制（"落后是常态"）。
被隔离的一方**不会报错**（它看到的是一份完整的、只是过时的世界），
所以**这个偏差可以持续几个月不被发现**。

**判据怎么改**：给"给外部看的副本目录"定一条硬规矩 ——
**每次交给对方之前，先问一句"上次同步是什么时候"，并刷新。**

更根本的修法：让副本可被**自动重建**（一个可反复跑的同步脚本），
而不是靠人记得。

**可复用规则**
- 凡是"镜像 / 副本 / 导出快照"，**必须有刷新机制或刷新纪律**，否则就是定时炸弹。
- 隔离方案设计时，**同时设计"如何让被隔离方拿到最新"**，这是一件事，不是两件。
- 排查"某个 Agent 判断异常"时，**先确认它看到的世界有多旧** —— 这比读它的推理过程更快。

## 06 · 判据太严 = 天天假红

**症状**：体检报告天天有告警，三周后没人再看它。

**现场**：第一版体检里加了「列数必须等于标准列数」。上线即报警 35 条。
逐条看过去 —— 全是**多行条目的续行**：条目正文换行后，续行自然没有 7 列。

**根因**：判据把"**正常的数据形态**"当成了错误。
条目内容是自由文本，**它本来就可能换行**。

**判据怎么改**：区分两种问题 ——

```python
# 真 error（会 fail）
重号 / ID 非单调 / 时间列不合规

# 仅提示（前缀 ⚠，不 fail）
列数不足
```

**为什么要区分**：因为**假红比不报更坏**。
一个常年亮着红灯的告警，训练出的不是谨慎，而是**忽略**。
等到真出问题时，它已经失去了信号价值。

**可复用规则**
- 写判据时问自己：**"这条告警，正常情况下会不会出现？"** 会 → 降级为提示。
- **宁可少判，不可误判。** 判据的信噪比比覆盖率重要。
- 上线新判据前，**先拿真实历史数据跑一遍**，看看会亮多少条。超过预期的 3 倍就重设计。

## 07 · 返回值会说谎：判据只能落在"结果"上

**症状**：批量删除文件，工具返回"失败"，但文件其实**已经被删掉了**。

**现场**：调系统 API 做批量移动到回收站，返回码是 `2`（按文档是错误）。
复查时发现**路径已经不存在** —— 操作成功了。

换个批次重试，返回 `124`，同样是"失败码"，同样**实际成功**。
第三次用别的路径，返回 `0`（成功）—— 但那次是**逐个删**的。

**根因**：批量操作系统 API 的返回码语义**不可靠**（可能是"部分成功"、
可能是"调用方式的问题"、也可能随实现细节变化）。
**把它当唯一判据，就等于把系统的真实状态交给一个会说谎的字段。**

**判据怎么改**：判据落到**可直接观察的结果**上 ——

```python
moved = not os.path.exists(src)      # 判据：源还在不在
```

而不是：

```python
if rc == 0: moved = True             # ❌ 返回码
```

**可复用规则**
- **"操作的返回值"和"操作的结果"是两件事。** 能验结果就别信返回值。
- 对"不可靠的返回码"（批量文件操作、跨进程通信、异步任务）一律**验终态**。
- 让这个判断**重复出现两次以上**后，就不要再说"可能是偶然" —— 把它写成规则。

## 08 · `0` 是假值：成功码被 `or` 吃掉

**症状**：命令行操作明明成功了，退出码却是 `3`（内部错误）。

**现场**：

```python
return int(res.get("code") or EXIT_INTERNAL)
```

成功时 `code = 0`。

**根因**：在多数语言里 **`0` 是假值**。
`0 or 3` → `3`。成功码被"兜底值"吃掉了。

这个 bug 的阴险之处：**它在失败路径上完全正常**（code=5 → 5；code=6 → 6），
只有**成功**的时候才错。所以测试如果只测失败路径，永远发现不了。

**判据怎么改**：

```python
code = res.get("code")
return EXIT_INTERNAL if code is None else int(code)      # 显式判 None
```

**可复用规则**
- 用 `or` 做"默认值"时，**先想清楚 0 / 空串 / 空列表是不是合法值**。
- 状态码、计数、索引这类字段，**一律显式判 `None`**。
- 写测试时，**成功路径和失败路径都要覆盖** —— 只测失败会漏掉这类 bug。

## 09 · 写进文件 ≠ 通知到位

**症状**：把新成员登记进了"注册表"，可**没有任何一个会话知道**。三周后才发现。

**现场**：注册表更新了、文档也写了、总线也登记了。
看起来"通知"做得很充分。

**根因**：**"通知"需要载体，而"文档"不是载体。**

| 类型 | 会不会自动进入上下文 | 算不算"得知" |
|---|---|---|
| 每次启动自动注入的配置文件 | ✅ 会 | ✅ **算** |
| 描述命中即触发的 Skill | ✅ 会 | ✅ **算** |
| 被读取的数据库字段（身份判定来源） | ✅ 会 | ✅ **算** |
| 手册、注册表、`docs/*.md` | ❌ 要主动读 | ❌ **不算** |

一份"要主动去读"的注册表，只是**可查证**，不是**已通知**。

**判据怎么改**：把"通知"落到**自动注入的那几处**，
并**逐个列出清单**（而不是笼统说一句"已同步"）。

**可复用规则**
- 判断"通知是否生效"，只问一句：**"它会自己读到吗？"**
- 新成员接入的标准动作里，**"注入点清单"是必填项**，不能只写"已更新注册表"。
- 同理适用于**规则变更**：改了一条规矩，只有写进"每次都会读"的地方才算生效。

## 10 · 归档校验的比对范围：判据要落在"本次产物"上

**症状**：归档功能**每次都会失败**，报"校验不通过"。

**现场**：归档逻辑是"把最老的 N 条搬进 `archive/`"，搬完做校验：

```python
got  = sorted(all_ids_in_archive_dir())    # ❌ 读整个归档目录
want = sorted(ids_being_moved)
if got != want: return "校验失败"
```

归档目录里**本来就有历史归档**（这是它的设计目的）。
于是第一次归档之后，第二次必然因为"集合多出旧条目"而失败。

**根因**：**判据的比对范围错了。** 要验的是"**本次写出的那个文件内容对不对**"，
不是"整个目录里有什么"。

**判据怎么改**：

```python
wrote = sorted(ids_in_file(just_written_file))    # ✅ 只看本次产物
if wrote != want: return "校验失败"
```

**可复用规则**
- 写"校验"时，先明确一句：**我在验什么的范围？**
  （本次产物 / 本次会话 / 整个目录 / 全历史）
- 累加型目录（archive / log / outbox）上的校验，**默认只验本次新增的部分**。
- 这个 bug 的隐蔽性在于：**它只在第二次运行时才暴露** —— 所以测试要从"空目录"和"有历史"两种初始状态各跑一遍。

## 附：这份清单怎么用

不要一次性全部实现。按这个顺序推进性价比最高：

1. **先做 01 / 02 / 03** —— 它们保护的是"记录本身"，一旦烂了，后面全白做。
2. **再做 06 / 07 / 08** —— 它们保护的是"你对系统的判断能力"。
3. **然后 04 / 05** —— 它们保护的是"时间维度的正确性"，需要定期复查。
4. **最后 09 / 10** —— 属于流程与运维层面。

还有一条不在上面的元规则，但可能是最重要的：

> **凡是你不得不"手动重跑一遍"才确认的事，都值得变成一条机械判据。**
